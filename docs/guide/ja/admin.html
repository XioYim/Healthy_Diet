09 / SERVER ADMIN

権威設定、クライアント表示、起動時登録をまず区別する。

サーバー管理者は設定ファイル、データパックオーバーレイ、ゲーム内エディターの3つの入口から編集できます。変更の種類によって更新方法が異なります。

ソース根拠：ConfigManager のファイルパス定数と ServerConfigFile.migrate。

02データパック定義と設定オーバーレイ

アイテムとツールチップ、栄養グループ、ステージ、ボーナス、品質、レアリティ、ブロックルールはデータパック定義に対応しています。config/healthy_diet/datapack/ を通じて本 MOD のローカルオーバーレイを提供します。

パス構造の例

config/healthy_diet/datapack/data/<名前空間>/healthy_diet/<種類>/<ファイル>.json

たとえば quality_levels/ は品質定義、blocks/ は右クリックブロックルールを保存します。その他の種類はゲーム内エディターに表示される実際のソースパスで特定してください。

エディターが保存した設定オーバーレイとワールド既存のデータパックが一緒に読み込まれます。変更前に対象項目のソースを確認してください。設定オーバーレイは、データを旧 config/healthy_diet/items/ にコピーすれば有効になるものではありません。

アイテム設定を特定する

まずアイテムの名前空間と ID を確認し、data/<名前空間>/healthy_diet/items/<アイテムパス>.json を探します。ツールチップも同様に healthy_diet/tooltips/ を使います。エディターが書き出した HD オーバーレイと他のデータパックの同一項目が同時に存在することがあります。オーバーレイを削除しても、下にデータパック定義が残っていればフォールバックし、そのアイテムを完全に無効化する保証はありません。

ソース根拠：ConfigManager の pack ローダー、PackJsonLoader、オーバーレイソース照会。

03/hdreload とその他のコマンド

/hdreload は OP4 が必要で、Healthy Diet 自身のリロード可能な設定とディスクオーバーレイだけを再読み込みし、オンラインプレイヤーにサーバー権威コンテンツを再送信します。Minecraft の完全な /reload ではありません。オーバーレイファイルを手動で追加・変更・削除した後は、種類ごとにリロード結果を確認できます。

プレイヤーとアイテム管理/headiet で栄養パネルを開きます。/hdui で手持ちアイテムと編集入口を管理し、/hdui stage で栄養ステージを管理します。
確認とヘルプ/hdhelp でプレイヤーがコマンド構文を確認できます。/hdtemperature は現在位置の温度内訳を報告し、/hdtrust は保護ホワイトリストを管理します。

管理コマンドはすべてのプレイヤーに開放されているわけではなく、権限は各コマンドの登録条件に従います。/hdreload は管理権限レベル4が必要です。/hdconfig はクライアントローカルコマンドで、実行自体に OP4 が必要です。専用サーバーコンソールのコマンドではありません。OP でないプレイヤーも他の画面からローカル外観設定に入れます。詳細は 設定画面の図解 を参照してください。

設定変更後の判断方法

HD オーバーレイを保存または更新した後、/hdreload を実行し、コマンドフィードバックとブロックの「ロード済み/バリアント/破棄」カウントを確認してから、実際のアイテムやブロックで検証します。エディターの一部の保存操作はすでに本 MOD のリロードを自動呼び出しします。ワールドデータパックや他の MOD リソースを変更した場合は、それぞれの読み込み手順に従う必要があり、/hdreload をバニラの /reload と見なせません。

ソース根拠：HDReloadCommand、HDUICommand、HDClientCommands。

04リロードだけでは反映されない変更

  • 1新しいアイテム ID の登録：登録定義は起動段階で有効になります。リロードは起動待ち計画を再計算するだけで、新しい実行時 ID を一時的に作成することはできません。
  • 2クライアントローカルファイル：たとえば display.json、ローカルグラデーション、霧効果などは、サーバーの /hdreload で強制的にリモート再読み込みされません。
  • 3スタック上限：アイテムレベル属性の変更には再起動が必要です。NBT バリアントごとに異なるスタック上限を持たせることはできません。

マルチサーバーで品質登録アイテムを追加する場合、クライアントはログイン前に一致した登録リストと関連リソースを取得し、登録手順に従って再起動する必要があります。「サーバー側のリロード完了」を「クライアントが新しい ID を取得済み」と見なさないでください。

更新方法を判断する3ステップ：サーバーでリロード可能なアイテム、ツールチップ、栄養データを変更 → /hdreload の読み込みフィードバックと配信を確認。プレイヤーのローカル表示/霧距離を変更 → 該当クライアントにローカル手順で再読み込みさせる。quality_registry/ の登録 ID を追加・削除、スタック上限を変更 → 起動時登録またはアイテム属性の要件に従って再起動。前の種類が配信済みでも、後の2種類が完了したことにはなりません。
ソース根拠：QualityRegistryEntry、ItemConfig.stackSize、HDReloadCommand、ConfigManager。
具体的な機能を確認しますか？章マップに戻り、栄養、保存期間、品質の章でプレイヤー向けの実際のルールを確認してください。

05よく使うコマンドと権限

コマンド権限用途
/hdhelp全員ゲーム内の完全なコマンド索引。ホバーで説明、クリックで入力欄に挿入。
/headiet全員自分の栄養パネルを開く。他人の閲覧は OP2、栄養値の変更は OP4。
/hdinfo [アイテム]全員メインハンドで一致するバリアントまたは指定アイテムの既定スタックを確認し、ローカルフードクエリビューアを開く。
/hdtemperature全員現在の温度ソース、ブロック貢献、利用可能な連動を診断。
/hdtrust全員自分のアイテム/コンテナの信頼プレイヤーリストを管理。
/hduiOP4メインハンドアイテムの設定センターを開く。
/hdui createOP4栄養グループ、品質レベル、レアリティ定義を管理。
/hdui stageOP4ステージ、進入コマンド、条件ボーナスを管理。
/hdui groups [プレイヤー]OP4プレイヤーの栄養値とグループ状態を管理。
/hdui tooltipOP4アイテムツールチップ編集入口を開く。バリアントがある場合は対応行を先に選択。
/hdui registryOP4起動時に登録される品質アイテムを管理。手持ちアイテムは不要。
/hdset rarityOP2アイテムにレアリティを指定または解除。詳細は /hdhelp を参照。
/hdcloneitemOP4オフハンドで設定済みの項目をメインハンドに部分的に上書き。クリアして完全置換するものではありません。
/hdreloadOP4本 MOD の設定をリロードし、オンラインプレイヤーに再送信。バニラの完全な /reload は起動しません。
/hdconfigクライアントローカル OP4クライアント設定画面を開く。専用サーバーコンソールには登録されません。
/titlepro などOP2TitlePro のタイトル、テンプレート、テーブル、消去、画面色オーバーレイ。

/headiet add、subtract、set の値変更は OP4 が必要です。/headiet clearaversion で指定アイテムの食物嫌悪記録を解除するには OP2 が必要です。/cleartoast で自分の実績トーストを消すのに権限は不要ですが、他のプレイヤーを指定する場合は OP2 が必要です。具体的な引数とターゲット選択はゲーム内の /hdhelp を使用し、過去のドキュメントの旧権限表をそのまま使わないでください。

ソース根拠：各コマンド登録クラスの権限条件。実際はゲーム内 /hdhelp とインストールされたファイルに準拠します。

06任意連動と再起動

任意 MOD用途
Jade対応するドロップ食品に保存期間情報を表示。
Legendary Survival Overhaul環境温度、体感温度などの利用可能なデータソースを提供。
Ecliptic Seasons季節、気候、関連する温度/保存の連動を提供。
Refurbished Furniture冷蔵庫/冷凍庫の保存に接続。NeoForge では framework も必要です。

これらは機能ごとの任意連動であり、基本プレイの前提ではありません。対象ゲームバージョンでサードパーティ MOD 自体が利用可能か確認してください。

再起動が必要な場合：起動時に登録される品質アイテムは、両側に一致する定義があり起動時に適用される必要があります。起動時コンテンツの変更は、ログイン後の同期や /hdreload だけでは反映されません。クライアントローカル表示ファイルの更新方法も、サーバーゲームプレイ設定とは異なります。
ソース根拠：QualityRegistryEntry、ConfigManager、各連動モジュールの準備判定。
